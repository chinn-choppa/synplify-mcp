# Политика безопасности

## Сообщение об уязвимости

Не создавайте публичный issue с работающим эксплойтом, токенами или закрытым RTL. Используйте **Report a vulnerability** на вкладке Security репозитория `synplify-mcp` после включения GitHub Private Vulnerability Reporting. Если функция пока недоступна — свяжитесь с сопровождающим проекта через приватный канал, не размещая технические детали публично.

## Модель угроз

MCP-клиент может передавать недоверенные параметры. В будущем сервер сможет запускать сторонний исполняемый файл с правами пользователя — это чувствительное действие даже для локального stdio.

Текущий прототип:

- по умолчанию не запускает EDA-продукт и не принимает произвольный shell/Tcl/DO; утверждённый `.prj` после явного включения может выполнять встроенный Tcl;
- не читает проектные исходники; отчёты `.srr` доступны только через заданный оператором `SYNPLIFY_MCP_WORKSPACE`;
- возвращаемые фрагменты отчётов могут содержать внутренние пути/имена; необходимо доверять MCP-клиенту и его модели;
- принимает ограниченный фрагмент текста для разбора диагностик;
- не открывает сетевых портов и не отправляет телеметрию;
- при поиске бинарника не передаёт абсолютные пути MCP-клиенту.

Перед внедрением запуска процессов обязательны: только доверенные бинарники, отсутствие `shell=True`, строгий root для входных и выходных путей, контроль символьных ссылок, время/память/размер логов, корректное завершение дочерних процессов и явное согласие пользователя на операции с побочными эффектами. MCP-аннотации `readOnlyHint` сами по себе не являются ограничением прав.

## Отдельные среды

Не подключайте внешний MCP к закрытым корпоративным исходникам через неутверждённую облачную модель. Локальный `stdio` не гарантирует, что результаты вызовов не покинут компьютер: это зависит и от самого MCP-клиента, и от модели агента.

## Поддерживаемые версии

До первого стабильного выпуска политика сроков исправления не установлена. Все уязвимости оцениваются индивидуально; список поддерживаемых веток появится вместе с первым релизом.

## Запуск синтеза (экспериментальная операция)

Сборка с помощью `run_approved_synthesis` доступна **только после** `SYNPLIFY_MCP_ENABLE_SYNTHESIS=1`, отдельного манифеста доверенных `.prj` с SHA-256 и абсолютного пути к бинарнику. Подтверждение внутри JSON не обеспечивает согласия человека: его обязан запросить MCP-клиент. Сам `.prj` содержит Tcl, его вложенные файлы и назначенные пути нужно дополнительно защищать операционной системой. Отдельный `cwd`/ограниченный stdout **не изолируют** произвольные побочные эффекты `.prj`. См. [APPROVED_RUN.md](docs/APPROVED_RUN.md). Ни лицензированные артефакты, ни исходники не публикуются в CI.

## Интеграционная модель доверия

Регистрация инструмента и MCP-аннотации о побочных эффектах не являются проверкой прав. Для `run_approved_synthesis` остаются обязательными отдельный флаг включения оператором, манифест утверждённых проектов и подтверждение в MCP-клиенте. Проверка SHA-256 .prj **не** охватывает изменяемые Tcl/RTL/includes, а локальная рабочая папка не ограничивает записи Synplify. Непроверенный контент запускайте только в изолированной VM/учётной записи с минимальными правами.

## Дополнительная граница alpha

При разрешении синтеза на Windows поддерживается только нативный `.exe`, а `.bat`/`.cmd`/`.ps1` отклоняются. Это **не** проверка подлинности исполняемого файла. Манифест утверждённых проектов должен храниться вне `SYNPLIFY_MCP_WORKSPACE` и вне доступа записи агента. Файлы Tcl, RTL, constraints и другие включения `.prj` остаются потенциально исполняемыми и изменяемыми: SHA-256 самого `.prj` их не защищает. Есть риск TOCTOU между хешированием и запуском. Используйте ограниченную VM/учётную запись и отдельный согласованный человеком запуск; встроенной песочницы нет.

**Alpha-ограничение:** запуск реального коммерческого EDA из MCP в `0.1.0a1` отключён независимо от `ENABLE_SYNTHESIS`; невозможно обойти это через параметр агента `acknowledge_side_effects`. Исполнительный код тестируется на макетах и требует отдельного hardening до включения.
