# Проверка fastmcp-slim: зависимости и полезные возможности

[English](FASTMCP_SLIM_REVIEW.en.md)

## Цель и границы

Отдельная ветка `experiment/fastmcp-slim-runtime`, основанная на
`experiment/fastmcp-v4` (черновой PR #16). Проверяется, получится ли
существенно сократить производственное окружение FastMCP и какие
дополнительные возможности реально помогают отдельному EDA-адаптеру.
Это не изменение `main` и не изменение PR #15 или #16.

Упрощение согласно официальным extras пакета версии 4.1.6:

- **Производство:** `fastmcp-slim[server]==4.1.6`, `mcp==2.3.0`.
- **Только разработка:** `fastmcp-slim[client]==4.1.6`
  в группе `[dependency-groups].dev`.
- Официальный MCP-клиент остаётся обязательной независимой проверкой
  `tools/list` и `tools/call` через настоящий subprocess `stdio`.
- В публичном CI используется `uv sync --no-dev` в **отдельных
  заданиях**, после чего выполняются `test_runtime_only.py`.
  Протокольные тесты не зависят от наличия FastMCP-клиента в
  производственном окружении.

`fastmcp-slim` без extra `[server]` не считается поддерживаемой
конфигурацией сервера. Сам FastMCP явно указывает на необходимость
`fastmcp-slim[server]` для серверных импортов. Ручная урезка его
внутренних транзитивных зависимостей не является безопасным способом
поддерживать публичный MCP-сервер.

## Фактические измерения

| Конфигурация | Установленных пакетов |
| --- | ---: |
| Исходный `mcp==2.3.0` как сервер | 29 |
| `fastmcp==4.1.6` как сервер | 63 |
| `fastmcp-slim[server]==4.1.6` + dev client | 62 |
| `fastmcp-slim[server]==4.1.6`, **без dev** | 62 |

Источник чисел: строки `Installed N packages` в GitHub Actions,
Linux `ubuntu-latest`, Python 3.13, `uv 0.13.0`.
Базовый SDK — [run #42203127472](https://github.com/chinn-choppa/synplify-mcp/actions/runs/42203127472),
полный FastMCP — [run #42213862834](https://github.com/chinn-choppa/synplify-mcp/actions/runs/42213862834),
slim — [run #42223925259](https://github.com/chinn-choppa/synplify-mcp/actions/runs/42223925259).
Оценивать сокращение **по `Installed`**, а не только
`Resolved`: разрешение может учитывать объявленные группы,
даже если конкретная синхронизация выполнена с `--no-dev`.
Упрощение экономит **1 пакет** относительно полного FastMCP,
но добавляет **33 пакета** к базовому официальному MCP SDK.

Это не сравнение размера файлов, зависимости могут иметь разный вес.
Сравнение времён отдельных CI-заданий не является воспроизводимым
бенчмарком производительности.

## Сравнение реальной работоспособности

[Run #42223925259](https://github.com/chinn-choppa/synplify-mcp/actions/runs/42223925259):
**12/12 заданий успешно**: Windows/Linux × Python 3.11/3.13/3.15.2,
шесть обычных заданий с **84 тестами каждое**, ещё шесть
`runtime-only` с **2 тестами каждое**.

Проверено:
- локальная регистрация и вызов всех шести MCP-инструментов;
- строгие входные схемы и отказ от непредусмотренных аргументов;
- независимый официальный MCP-клиент в отдельном процессе;
- отказ `run_approved_synthesis` при выключенном разрешении;
- безопасное чтение и сравнение **синтетических** отчётов;
- запуск в окружении, где `fastmcp-slim[client]` не установлен;
- два **только тестовых**, не включённых в продукт примера
  дополнительных возможностей FastMCP.

## Практическая ценность FastMCP для наших EDA-серверов

| Возможность | Проверка | Решение для отдельных Synplify/Verilator/Questa |
| --- | --- | --- |
| Строгая проверка неизвестных аргументов | Проверена через независимый MCP-клиент | Полезна, но не требует перехода на FastMCP |
| Объединение двух серверов через `mount(namespace=...)` | Синтетический тест успешно вызывает оба разных `tool_status` | Не нужно, пока три адаптера развёртываются и изолируются раздельно |
| Middleware `on_call_tool` | Считает вызовы, не сохраняет аргументы | Можно использовать позднее для приватной диагностики и лимитов |
| HTTP/proxy/OAuth | В эксперимент не включались | Не требуется для локального `stdio`; увеличит поверхность атаки |
| Безопасность запуска EDA | Не решается фреймворком | Контроль `.prj`/Tcl/прав ОС остаётся в `approved_run.py` и среде исполнения |

Синтетические тесты композиции НЕ подтверждают интеграцию трёх
реальных серверов или совместную работу с лицензиями. Объединение
EDA-адаптеров в один процесс может сделать границы доступа более
размытыми: отдельные настройки, разрешённые каталоги, лицензии и
ресурсные лимиты лучше сохранять независимо.

## Решение

**Рекомендовано оставить `MCPServer` из официального MCP SDK
в основной реализации.** Причины: проверенная матрица, меньше
зависимостей, отсутствие необходимости в композиции, HTTP и
универсальном middleware на текущем этапе.

FastMCP полезен как **отложенный вариант архитектуры**, если появится
обоснованная потребность в EDA-хабе или сложном наборе middleware.
Оба экспериментальных PR необходимо оставить черновиками,
не сливать в `main` и не переносить изменения автоматически
в Questa/Verilator MCP.

Ни одна проверка не запускает коммерческий Synplify Pro:
`EDA_PASS=NOT_RUN`. Для воспроизводимого выпуска также остаётся
задача создать и проверить `uv.lock` по поддерживаемым платформам.
