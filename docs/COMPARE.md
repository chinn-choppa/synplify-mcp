# Сопоставление отчётов сборок (.srr)

[English](COMPARE.en.md)

## Инструмент

`compare_srr_reports(baseline_path, candidate_path, encoding="auto")`
сравнивает два **разрешённых локальных** `.srr`-файла. Пути относительны
к `SYNPLIFY_MCP_WORKSPACE`. Операция не вызывает Synplify, не изменяет
RTL или артефакты, не отправляет журналы во внешние сервисы и не
исполняет Tcl/shell.

Оба отчёта проходят те же проверки размера (1 МиБ на файл),
кодировок, символьных ссылок и выхода за workspace, что и `parse_srr`.
Оригиналы сопоставляются по SHA-256. Имена Git-ревизий не извлекаются
из отчёта и **не выдумываются**: `baseline` и `candidate` —
это входные файлы, а не автоматически проверенные коммиты.

## Контроль сопоставимости

Результат возвращает `state`, `context`, `diagnostics`,
`resources`, `timing`, `baseline` и `candidate`.

- Для численного сравнения ресурсов требуются **явно известные и
  одинаковые** `tool_version` и `device` в обоих отчётах.
  Отсутствие метаданных → `UNVERIFIED`; конфликт →
  `INCOMPATIBLE`, без числовых дельт.
- Для ресурсов требуется состояние `PARSED` у обеих сторон;
  используются исходные названия примитивов и `unit="count"`.
  Если ресурс отсутствует в одной сборке либо `available` изменился,
  число для него не считается сопоставимой дельтой.
  Умолчания вида «ресурс отсутствует → 0» **запрещены**.
- Диагностики сопоставляются по уровню, коду, категории, пути RTL,
  координатам и тексту. Сохраняется происхождение исходных строк.
  Изменения в усечённых/неопознанных отчётах помечаются
  `PARTIAL_OBSERVATION` и не доказывают отсутствие других ошибок.
- Временные характеристики: проверяется идентичность набора тактов,
  известных запросов и единиц периодов/частот; иначе
  `UNKNOWN_CONSTRAINTS`, `INCOMPATIBLE_CLOCK_REQUESTS` или
  `INCOMPATIBLE_CLOCK_SET`.
  **Даже совпадающие запросы частот не означают, что неизменны все
  исключения, SDC/FDC, группы тактов, I/O delay и ограничения.**
  Поэтому для timing показываются только наблюдавшиеся значения
  `estimated` и `slack` с происхождением, а
  `estimated_delta/slack_delta=null`. Состояние
  `UNVERIFIED_FULL_CONSTRAINTS`; улучшение не заявляется.
- Все временные значения относятся к
  `SYNTHESIS_ESTIMATE`, `implementation_timing=false`,
  **не post-place-and-route**, в том числе для Virtex-4 и других
  старых Xilinx FPGA.

`synthesis_status="UNKNOWN"` и `executed=false` неизменны для
этого инструмента. Одинаковые байты файлов могут дать
`IDENTICAL_BYTES`, но это **не** `EDA_PASS`.

## Ограничения данных

В ответах возвращаются только краткие свидетельства (начало исходной
строки до 256 символов), номера строк и байтовые смещения, привязанные
к SHA-256 файла; **не полные журналы**. Список изменений ограничен
16 записями на категорию, численность диагностик и размеры входных
данных ограничены исходным парсером. При отказе чтения возвращаются
`INPUT_ERROR`, сторона и `error_code` без раскрытия полного пути.

Сопоставление сообщений не означает подтверждённую работу Synplify:
примеры `compare_base.srr` и `compare_changed.srr` придуманы для
проекта. Реальная совместимость версии EDA остаётся `NOT_RUN`.
Программа не может гарантировать, что два файла соответствуют двум
названным пользователем Git-ревизиям — это должно проверяться отдельно.

## Пример MCP-вызова

```json
{
  "baseline_path": "reports/before.srr",
  "candidate_path": "reports/after.srr",
  "encoding": "auto"
}
```

Настройка workspace и предупреждение о передаче содержимого отчётов
MCP-клиенту описаны в [руководстве парсера](SRR_PARSER.md).
