# Запуск заранее утверждённого Synplify-проекта (эксперимент)

[English](APPROVED_RUN.en.md)

## Почему запуск ограничен

Synplify Pro поддерживает команду `synplify_pro -batch <project.prj>`,
но сам файл `.prj` содержит **Tcl-команды**. Следовательно,
`subprocess(shell=False)` **не является** достаточной защитой:
проверяйте проект и его зависимости, ограничения и политику ОС.
Только заранее утверждённые оператором проекты допустимы.
[Исследовательская ссылка на режим batch](https://www.arl.wustl.edu/projects/fpx/cse535/resources/synpro_ref_1001.pdf);
лицензионные возможности режима batch отличаются по редакциям.
В репозитории **нет** фирменных материалов/бинарников.

## Требования к оператору

Подключать этот инструмент к доверенному MCP-клиенту разрешено только после
проверки локального проекта и его включений. Не используйте его на
враждебных `.prj`, не доверяйте одному лишь SHA-256 при изменяемых
`add_file` / Tcl / HDL-зависимостях. Для жёсткой изоляции применяйте
операторскую VM/контейнер с ограничениями доступа и сети: функция **не
создаёт изолированную ОС-песочницу**, а лишь отдельный каталог для
собственного журнала и текущего рабочего каталога процесса.

Оператор создаёт доверенный workspace (например `/srv/eda/workspace`)
с каталогами `projects/` и `artifacts/` и проектом
`projects/demo.prj`. Пути проекта и каталога артефактов
**относительны к workspace** и не должны быть символьными ссылками.
Каталог артефактов предварительно существует и не должен содержать
утверждённый `.prj`.

Создайте **вне области редактирования агентом** небольшой JSON-файл:

```json
{
  "schema": 1,
  "projects": {
    "demo": {
      "project": "projects/demo.prj",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "artifacts": "artifacts"
    }
  }
}
```

В примере приведён условный SHA-256: замените его на **реальный** хеш `.prj`.
На Linux хеш можно получить через `sha256sum projects/demo.prj`,
на Windows — `Get-FileHash ... -Algorithm SHA256`.

Экспортируйте переменные **при запуске сервера, а не через параметры MCP**:

```bash
export SYNPLIFY_MCP_ENABLE_SYNTHESIS=1
export SYNPLIFY_MCP_WORKSPACE=/srv/eda/workspace
export SYNPLIFY_MCP_RUN_MANIFEST=/srv/eda/operator/manifest.json
export SYNPLIFY_MCP_EXECUTABLE=/opt/synopsys/synplify/bin/synplify_pro
uv run synplify-mcp
```

В Windows используйте `$env:SYNPLIFY_MCP_... = "..."` и реальные
абсолютные пути. Пример местоположения исполняемого файла выше —
**условный** и не доказывает наличие Synplify в этой директории.

## MCP-вызов с побочными эффектами

```json
{
  "project_id": "demo",
  "acknowledge_side_effects": true,
  "timeout_seconds": 30
}
```

**Важно:** поле `acknowledge_side_effects=true` может установить агент.
Оно **не гарантирует подтверждения человеком**. Настройте в MCP-клиенте
обязательное подтверждение операции, кроме установки явного серверного
разрешения; не предоставляйте эту команду ненадёжным агентам.

Сервер вызывает только список аргументов
`[SYNPLIFY_MCP_EXECUTABLE, "-batch", <утверждённый путь .prj>]`
без `shell=True`, `-tclcmd` и произвольного Tcl. Время 1–120 с;
поток stdout/stderr сохраняется только локально, не более 64 КиБ
в `stdout.log` каждого запуска; при превышении лимита процесс
прерывается. Тайм-аут/завершение группы процессов:
`killpg` в POSIX и системный `taskkill /T` в Windows —
**наилучшая попытка**, а не абсолютная изоляция всех потомков.

## Результат и ограничения

`state` различает:

- `DISABLED`, `CONFIRMATION_REQUIRED`, `PROJECT_NOT_APPROVED`,
  `PROJECT_CHANGED`, `INVALID_MANIFEST`, `NOT_INSTALLED` и
  другие причины отказа **без исполнения**;
- `LICENSE_UNAVAILABLE` (эвристика по ограниченному журналу),
  `TOOL_FAILED` (ненулевой exit code), `TIMEOUT`,
  `LOG_LIMIT`, `LAUNCH_ERROR`;
- `PROCESS_EXIT_ZERO_UNVERIFIED`: процесс завершился с кодом 0,
  но **успех Synplify не подтверждён**. Всегда
  `eda_validation="NOT_VERIFIED"`. Никакого `EDA_PASS` на
  основании кода возврата/отсутствия ошибок.

Результат содержит только `project_id`, SHA-256 утверждённого файла
`.prj`, краткий ID каталога запуска, код возврата и SHA-256
**сохранённой части** локального журнала. Абсолютные пути и
содержимое stdout не включаются в ответ MCP. Запуск EDA может сам
использовать локальную/сетевую службу лицензий по настройкам оператора —
сервер не отправляет лицензионные файлы и отчёты наружу.

Каталог `artifacts/synthesis-...` ограничивает **cwd и собственный
журнал сервера**, но настоящий Synplify может писать по путям,
указанным в доверенном `.prj`. Полная проверка выходных файлов,
обработки лицензии и реального выполнения в коммерческих версиях —
`NOT_RUN`. Публичный CI выполняет только mock-процессы и проверки
запрещённых операций; для реальной приёмки нужен установленный
лицензионный Synplify в отдельной доверенной среде.

## Уточнения безопасности для alpha

- На Windows `SYNPLIFY_MCP_EXECUTABLE` должен указывать на нативный `.exe`; `.bat`, `.cmd`, `.ps1` отклоняются, поскольку пакетные файлы могут запускаться через командный процессор даже при `shell=False`. Расширение не подтверждает подлинность бинарника.
- Манифест разрешённых проектов **обязан находиться вне `SYNPLIFY_MCP_WORKSPACE`**, иначе агент, редактирующий исходники проекта, потенциально сможет изменить собственные разрешения. Путь контролирует оператор.
- Проверка хеша `.prj` не защищает его Tcl, HDL, constraints или включённые файлы от изменения между проверкой и запуском. Непроверенные проекты — только в отдельной ограниченной VM/учётной записи. Этот запуск не является песочницей ОС.
